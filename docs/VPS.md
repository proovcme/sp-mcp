# Развёртывание веб-интерфейса на VPS

Публичный интерфейс: **https://locia.work/sp/**.
Это Python-сервис за Caddy, а не статическая копия страницы. МегаНорм и официальный каталог
запрашиваются с VPS. Поиск, редакции, оглавление и проверка статуса используют одну серверную
SQLite-базу. С локальной базой компьютера она автоматически не синхронизируется.

Примеры конфигурации: [systemd](../deploy/sp-mcp.service), [Caddy](../deploy/sp.caddy).
Установка выполняется из опубликованного wheel; зависимости фиксируются из `uv.lock`:

```bash
uv export --locked --no-dev --no-emit-project --no-hashes --output-file requirements.txt
# На сервере, после передачи wheel и requirements.txt:
python3 -m venv /opt/sp-mcp/venv
/opt/sp-mcp/venv/bin/pip install -r /opt/sp-mcp/requirements.txt /opt/sp-mcp/sp_mcp-0.2.6-py3-none-any.whl
useradd --system --home-dir /var/lib/sp-mcp --shell /usr/sbin/nologin sp-mcp
install -m 0644 deploy/sp-mcp.service /etc/systemd/system/sp-mcp.service
systemctl daemon-reload
systemctl enable --now sp-mcp
```

Сервис слушает только `127.0.0.1:62813`; Caddy удаляет префикс `/sp` и передаёт
исходный Host и HTTPS-схему. Относительные пути ресурсов и API сохраняют работу под `/sp/`.
Список `SP_MCP_ALLOWED_HOSTS` в службе должен включать домен, который передаёт обратный прокси.
При обновлении существующей службы установите это значение до запуска новой сборки.
Маршрут `/sp/` явно использует gzip, в том числе когда браузер предлагает несколько вариантов
сжатия. При проверке статических ресурсов нужно читать ответ целиком, а не только его статус:
недогруженный JavaScript оставляет оболочку без результатов и действий.
Импорт `sp.caddy` добавляется внутрь существующего блока сайта. Перед reload необходимо сохранить
предыдущую конфигурацию и выполнить `caddy validate --config /etc/caddy/Caddyfile`.

Публичный маршрут разрешает только интерфейс и операции с нормативами. MCP и операции
с проектами «Увязки» через него недоступны. На VPS не переносятся частные проекты, локальные
настройки, ключи и модель эмбеддингов. Связь с частной «Увязкой» требует отдельного защищённого
подключения и не появляется от публикации сайта. Рабочая локальная интеграция сохраняется.

`systemd` запускает процесс от отдельного пользователя, сохраняет данные в `/var/lib/sp-mcp`,
ограничивает память и CPU, автоматически запускает сервис после перезагрузки. Поиск работает без модели.
При `SP_MCP_PUBLIC_LIMITS=1` разрешены одна тяжёлая операция и до четырёх API-запросов одновременно;
ожидающая очередь не создаётся. Тяжёлые операции ограничены шестью в минуту с одного адреса и двенадцатью
в минуту суммарно; чтение сохранённых документов имеет отдельный бюджет. Занятость возвращает 503,
превышение частоты — 429, оба ответа содержат `Retry-After`. Пакетная проверка публичного сервера принимает до двух документов.
Поиск и пакетная проверка имеют общий бюджет сетевых обращений на операцию: по умолчанию 60 секунд и до 36 запросов,
включая проверки robots.txt и перенаправления. Поиск сообщает о частичном результате при исчерпании бюджета.
Перед новыми тяжёлыми операциями проверяются порог данных 512 МиБ и свободный резерв диска 1 ГиБ.
При достижении порога новые операции останавливаются, сохранённые документы можно читать.
Это проверка перед операцией, а не файловая квота; завершившаяся операция может превысить порог.
Предел процесса — 448 МиБ RAM и 75% одного CPU; эти ограничения отделяют его от остальных сервисов VPS.
Для копии базы используется SQLite backup API; простое копирование работающего файла не подходит.

Проверка после развёртывания:

1. `GET /sp/health`, загрузка JS/CSS и `POST /sp/api/library`.
2. Холодный запрос в каталогах, открытие текста, оглавление и переход к разделу.
3. Проверка статуса через официальный источник: результат содержит фактические evidence,
   а конфликты и ошибки не подменяются подтверждением актуальности.
4. Отдельно проверить браузерный Origin через HTTPS; MCP и маршруты проектов должны возвращать 404.
5. Проверить `systemctl status sp-mcp`, потребление памяти и журнал ошибок.
